# Showcase and Profiles as documentation

Bring `/showcase` and `/profiles` to the same documentation style as `/commands` (see `docs/userstories/commands-docs-layout/README.md`): a left sidebar and one section per topic.

Design approved by the user in chat on 2026-10-28, including deleting `TerminalMockup` and `DesktopAppMockup` once they are unused. Execution mode: all stories (approved 2026-10-28).

## Constraints

- Every user-facing string in English and Spanish; flags, commands, and identifiers stay in English.
- Existing `docs-*` styles and design tokens; no new libraries.
- Pages and components re-render on the language toggle.
- Source code is generated by the local model first (`AGENTS.md`); the agent reviews, applies, and verifies. Section text is data checked against `../../Desktop/llmtuner`.
- `/commands` must look and behave exactly as before.

## US-01 — Shared documentation layout

As a maintainer, I want one component that renders a docs page, so that `/commands`, `/showcase`, and `/profiles` share the same sidebar and section markup.

**Acceptance criteria**

1. A component in `Components/` renders the mobile menu, the sticky sidebar, and the sections of a list of `DocSection`, for a given list of groups (id and localized label) and the page route used in anchors.
2. It lets a page add extra content at the end of a given section (used for the command builder and the profile comparison table).
3. `DocSection` gains an optional image (path and alt text) that the component renders with the existing visual style.
4. `Pages/Commands.razor` uses the component; its output is unchanged (same 18 sections, anchors, builder, and responsive behavior).

**Dependencies**: none.

**Verification**: `dotnet build`; on `/commands`, the same section count, sidebar links, builder, and 375 px behavior as before.

**Status**: complete

## US-02 — Showcase as documentation

As a visitor, I want each real screenshot explained in its own section, so that I can follow the CLI and the desktop app screen by screen.

**Acceptance criteria**

3. Captions come from the current mockups, corrected where they no longer match llm-tuner 0.5.0.
4. `TerminalMockup.razor` and `DesktopAppMockup.razor` are deleted.

**Dependencies**: US-01.

**Verification**: preview `/showcase` in English and Spanish; all 13 images load (`naturalWidth > 0`); sidebar links; 375 px without horizontal scroll.

**Status**: complete

## US-03 — Profiles as documentation, with corrected facts

As a visitor, I want each load profile explained accurately, so that I pick the right one.

**Acceptance criteria**

1. `/profiles` uses the shared layout with sections: How profiles work, `speed`, `balanced`, `quality`, Variant switching, When it measures again, Comparison.
2. Each profile section states its goal, model variant, allowed KV types, trade-off, when to use it, and an example command with `--profile`.
3. The facts follow the llm-tuner README: `speed` uses the lightest downloaded variant and any KV type (`f16`, `q8_0`, `q4_0`); `balanced` (default) uses the selected variant and ranks by `tps × kvQuality`; `quality` uses the heaviest variant that fits fully in VRAM with `f16` or `q8_0`, and falls back to `balanced` when nothing fits. The current summary cards that say otherwise are removed.
4. The comparison table (`ProfileComparator`) stays as the last section, with any wrong values in `GetProfiles()` fixed.

**Dependencies**: US-01.

**Verification**: compare each statement with the llm-tuner README; preview in English and Spanish at 1280 and 375 px.

**Status**: complete
